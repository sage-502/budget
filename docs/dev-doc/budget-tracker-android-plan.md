# Budget Tracker Android 전환 기획서

> 기존 PWA 버전(`sage-502/budget-app`)의 localStorage 데이터 손실 사고를 계기로,
> 확장/유지보수가 쉬운 구조의 네이티브 안드로이드 앱으로 재구축하는 기획입니다.

| 분류 | 이전 버전 | 신규 버전 |
|---|---|---|
| 형태 | 웹 PWA | 안드로이드 네이티브 앱 |
| 데이터 저장 | localStorage (단일 JSON blob) | Room (SQLite, 정규화된 테이블) |
| 백업 | 수동 JSON export/import | 수동 백업 유지 + 가져오기 확인 절차 추가 |
| 확장성 | 카테고리·구조 하드코딩 | 카테고리 커스텀, 반복 지출, 설정 화면 지원 |

---

## 01. 전환 배경 및 목표

이전 버전은 앱 전체 데이터가 `budgetAppData`라는 **단일 localStorage 키**에 통째로 저장되는 구조였습니다. 이 방식은 브라우저 데이터 삭제, 캐시 초기화, 오작동 한 번으로 전체 기록이 사라질 수 있는 구조적 위험을 가지고 있었고 실제로 그 일이 벌어졌습니다.

이번 전환의 목표는 두 가지입니다.

1. **데이터 안정성** — SQLite(Room) 기반으로 전환해 "앱 데이터 하나가 통째로 날아가는" 구조적 위험을 제거.
2. **확장 용이성** — 카테고리·반복 지출·통계 같은 기능을 앱 재설계 없이 추가할 수 있는 구조로 설계.

클라우드 백업/동기화는 이번 범위에 포함하지 않습니다. (수동 백업 방식 유지, 단 안전장치는 보강)

## 02. 기술 스택 (제안)

| 영역 | 선택 | 비고 |
|---|---|---|
| 언어 | Kotlin | 안드로이드 표준, 유지보수 용이 |
| UI | Jetpack Compose | 화면 추가/변경 시 XML 레이아웃보다 수정 비용 낮음 |
| 로컬 DB | Room (SQLite) | 마이그레이션 버전 관리 지원, 데이터 정합성 보장 |
| 아키텍처 | MVVM + Repository 패턴 | UI ↔ 데이터 계층 분리로 기능 추가 시 영향 범위 최소화 |
| 비동기 | Kotlin Coroutines + Flow | DB 변경사항 UI 자동 반영 |
| 반복 작업 | WorkManager | 반복 지출 자동 등록 스케줄링 |

> 스택 관련 결정은 추정 기반 제안입니다. 특정 라이브러리 경험이 있다면 그에 맞춰 조정 가능합니다.

## 03. 정보 구조 & 화면 흐름

하단 탭 4개로 구성 (기존 Budget 탭은 Settings 내부 메뉴로 편입).

| 탭 | 화면 | 내용 |
|---|---|---|
| Tab 1 | **Dashboard** | 월 전체 + 카테고리별 예산 카드, 진행 바 |
| Tab 2 | **Add** | 금액·카테고리·결제수단·날짜·메모 입력, 반복 지출 등록 옵션 |
| Tab 3 | **Transactions** | 전체 거래 목록, 정렬/필터, 수정/삭제(삭제 시 확인 절차) |
| Tab 4 | **Settings** | 예산 설정, 카테고리 관리, 반복 지출 관리, 백업/복원, 통계 |

Settings 탭은 목록형 메뉴 화면으로 구성하고, 각 항목(예산 설정 / 카테고리 관리 / 반복 지출 / 백업·복원 / 통계)을 하위 화면으로 진입하는 구조를 권장합니다. (기존 Budget 탭의 "월 삭제" 기능은 예산 설정 하위 화면에 유지)

상단 월 이동(◀ / ▶)은 유지. 각 월은 독립된 예산·거래 데이터를 가지는 구조도 유지합니다.

## 04. 데이터 모델 (Room 엔티티)

기존 "단일 JSON blob" 구조를 테이블 단위로 정규화합니다. 이렇게 하면 카테고리 추가, 반복 지출처럼 새 개념이 생겨도 기존 테이블을 건드리지 않고 테이블만 추가하면 됩니다.

```
Category (신규 — 하드코딩 탈피)
 ├ id (PK)
 ├ name
 ├ icon
 ├ color
 ├ isDefault (기본 7종 여부)
 ├ isActive (삭제 = 비활성화, 물리 삭제 아님)
 └ sortOrder

PaymentMethod (신규 — 하드코딩 탈피)
 ├ id (PK)
 ├ name (카드 / 현금 / 계좌 등)
 ├ isDefault (기본 3종 여부)
 ├ isActive
 └ sortOrder

Budget
 ├ id (PK)
 ├ monthKey ("2026-08")
 ├ categoryId (FK → Category)
 └ amount

Transaction
 ├ id (PK)
 ├ amount
 ├ categoryId (FK → Category)
 ├ paymentMethodId (FK → PaymentMethod)
 ├ date
 ├ memo
 └ recurringId (FK → RecurringExpense, nullable — 반복 지출로 생성된 경우 출처 추적)

RecurringExpense (신규)
 ├ id (PK)
 ├ categoryId (FK → Category)
 ├ paymentMethodId (FK → PaymentMethod)
 ├ amount
 ├ dayOfMonth
 ├ memo
 └ isActive
```

**결제수단도 카테고리와 동일하게 테이블로 분리**했습니다. 이전 버전은 `card/cash/account`가 코드에 고정돼 있었지만, 신규 구조는 사용자가 결제수단을 추가·이름변경·비활성화할 수 있습니다. 삭제 처리 방식도 카테고리와 동일하게 물리 삭제 대신 비활성화를 사용합니다.

**개선 포인트**: 기존에는 카테고리가 `food/house/transport/...` 문자열로 코드에 박혀 있었지만, 신규 구조는 `Category` 테이블 자체가 데이터이므로 사용자가 앱 안에서 추가/이름 변경/삭제를 할 수 있습니다.

**카테고리 삭제 처리 (확정)**: 물리 삭제 대신 `isActive = false`로 처리하는 소프트 삭제를 채택합니다. 완전 삭제 시 해당 카테고리로 기록된 과거 Transaction의 FK가 깨지거나 과거 지출이 왜곡될 수 있기 때문입니다. 비활성화된 카테고리는 카테고리 선택 목록(Add, 예산 설정)에서는 제외되지만, 과거 거래 내역과 통계에는 그대로 표시되며 필요 시 복구도 가능합니다.

## 05. 핵심 기능 명세

| 기능 | 설명 | 이전 대비 변경점 |
|---|---|---|
| 카테고리 관리 | Settings > 카테고리 관리에서 추가/이름변경/색상변경/순서변경/삭제(비활성화) | 신규 — 하드코딩 제거 |
| 반복 지출 등록 | Add 또는 Settings > 반복 지출에서 카테고리·결제수단·결제일을 사용자가 직접 지정 → WorkManager가 매월 해당 결제일에 자동으로 Transaction 생성 | 신규, 결제일 사용자 지정 확정 |
| 예산 설정 | Settings > 예산 설정에서 카테고리별 월 예산 입력, 신규 카테고리 추가 시 기본값 0으로 시작, 월 삭제 기능 포함 | 탭 → Settings 하위 메뉴로 편입 |
| 대시보드 진행률 | 전체/카테고리별 소진율 프로그레스 바, 초과 시 경고 | 유지 |
| 카테고리 상세 조회 | 대시보드 카드 클릭 시 해당 카테고리 거래만 모아 보여줌 (바텀시트) | 이전 버전에서 누락 없이 그대로 계승, UI만 팝업 → 바텀시트로 변경 |
| 거래 CRUD | 입력/수정/삭제, 반복 지출로 생성된 거래는 출처 표시. **개별 거래 삭제 시 확인 다이얼로그 추가** | 이전 버전은 개별 삭제에 확인 절차가 없어 즉시 삭제됨 — 보완 |
| JSON 백업/복원 | Settings > 백업/복원에서 파일로 내보내기/가져오기 | **가져오기 시 확인 다이얼로그 추가**, **파싱 실패 시 에러 알림 처리 추가** (이전 버전은 확인 절차도 예외 처리도 없어 잘못된 파일 선택 시 곧바로 오류로 이어짐) |
| 통계 | Settings > 통계, 월별 총지출 vs 총예산을 막대 그래프로 표시 (카테고리별 비교는 Dashboard에서 이미 제공) | 신규, 형태(막대 그래프, 예산 초과분 별도 표시) 확정 |

## 06. 확장성을 위한 설계 원칙

이번 재구축의 핵심 목적이 "다음에 기능을 또 추가하기 쉬운 구조"이므로, 아래 원칙을 코드 레벨에서 지킵니다.

- **Repository 인터페이스 분리** — ViewModel은 Room을 직접 호출하지 않고 Repository 인터페이스를 통해서만 접근. 나중에 클라우드 동기화를 붙이더라도 Repository 구현체만 교체하면 되고 UI/ViewModel은 변경 불필요.
- **카테고리를 데이터로 취급** — 열거형(enum)이 아닌 DB 테이블로 관리해 사용자 커스텀이 코드 수정 없이 가능.
- **Room 마이그레이션 스크립트 필수화** — 스키마 변경 시 항상 `Migration` 객체 작성. `fallbackToDestructiveMigration()` 사용 금지 (이걸 쓰면 예전과 같은 데이터 손실 위험이 재발함).
- **기능별 모듈 경계** — 반복 지출, 통계, 백업 등은 각각 독립된 패키지로 분리해 한 기능 수정이 다른 기능에 영향을 주지 않도록 함.

## 07. 이전 버전에서 이어받는 제약 (변경 없음)

- 무료·무광고, 계정 없음, 단일 기기 기준 — 유지
- 클라우드 동기화 없음 — 이번 범위에서 제외 (추후 별도 논의 가능)

## 08. 마이그레이션 (기존 사용자 데이터 이전)

localStorage 데이터가 남아있는 기기가 있다면, 기존 JSON export 포맷을 신규 앱의 "가져오기" 기능이 인식해서 Category/Budget/Transaction 테이블로 분해 저장하는 1회성 임포터가 필요합니다. (단, 이번 사고로 기존 데이터가 유실됐다면 이 항목은 해당 없음)

## 09. 확정 사항 요약

- 반복 지출: 카테고리·결제수단·결제일 모두 사용자가 직접 지정
- 통계 화면: 월별 총지출 vs 총예산을 막대 그래프로 표시 (예산 초과분 별도 색상), 카테고리별 비교는 Dashboard에서 별도 제공
- 카테고리 삭제: 물리 삭제 대신 비활성화(소프트 삭제) 방식 채택
- Budget 화면: 별도 탭이 아닌 Settings 탭 하위 메뉴로 편입
